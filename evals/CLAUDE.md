# evals/

Offline evals that measure what unit tests cannot: calculator correctness on the
spec's hand-worked examples now, and extraction, categorization, explanation and
recurring-detection quality as those features land.

## Run

```
make eval                                                     # free suites, no API spend
make eval-llm                                                 # LLM suites, capped by EVAL_MAX_COST_CENTS
uv run python -m evals.run --suite calc --max-cost-cents 0    # one suite
uv run python -m evals.run --suite free --max-cost-cents 0 --report evals/results/run.json
```

Run from the repo root (`evals` is imported as a package). Exit code 0 means
every metric met its baseline, 1 a regression, 2 the cost cap or bad arguments.

## Layout

- `run.py`: CLI, suite selection (`free`, `llm`, `all` aliases), baseline comparison.
- `suites/base.py`: `Suite`, `SuiteResult`, `Budget`. `suites/__init__.py`: the registry.
- `suites/<name>.py`: one module per suite exposing `SUITE`.
- `fixtures/<suite>/`: inputs and labels. `fixtures/calc/*.json` holds spec
  examples as `[{"id", "route", "request", "expected"}]`.
- `fixtures/transactions.csv`: 534 synthetic labeled transactions
  (`id, merchant_raw, amount_cents, posted_at, category`) shared by the
  categorization suites: 500 generated by `gen/transactions.py` from a fixed
  seed, then the 15 `SIGN_CASES` written by hand for direction (spec 003 rules
  3a-3b and 5a: paychecks named like merchants, loan and card ledger language,
  `Interest` both ways, two refunds), then the 13 `NAME_CASES` for rule 3d
  (businesses whose names begin with an ordinary word a seed rule names a
  merchant by, such as `spectrum health` and `adobe grill`, and three bare
  descriptors the narrowed exact rules still label), then the 6
  `DEFINITION_CASES` for rule 9b (warehouse clubs and credit card payments no
  seed rule names, `H&R BLOCK`, and the IRS refund deposit, money in, which
  is `income`). Append hand-written rows after these so rows 1-500 never
  change. `uv run python -m evals.gen.transactions`
  rewrites it; a test fails if the committed file differs from a fresh
  generation, so change the generator, never the CSV.
- `suites/categorization_rules.py` (`categorization-rules`, free): the seed
  rules alone over that CSV, each row matched with its amount. `rules_precision` is the share of rule-labeled
  rows labeled correctly; `rules_coverage` is the share a rule labels, so
  `1 - rules_coverage` is the share that would go to the LLM. Baseline
  (October 30, issue #148 and spec 003 rule 9b): `rules_precision` 1.0,
  `rules_coverage` 0.7772 over 534 rows (0.7841 over the first 528); before the seed rules named their merchants it was 0.9714 and 0.8155, the
  misses `rent the runway` (housing), `target optical` (shopping) and
  `shell beach surf shop` (transport).
- `suites/categorization.py` (`categorization`, LLM): the same rows the
  way `categorize.run` labels them (spec 003 rule 29): seed rules, then each
  unknown merchant and direction's newest row to Sonnet (`LLM_MODEL_CATEGORIZE`), 50 per call, the label
  applied to every row of that merchant and direction. `accuracy` (all rows) and `llm_accuracy` (rows
  the model labeled); baseline measured on October 30 on `categorize/v3`
  (1.0 and 1.0 in three runs, one to two cents each; 33 merchants and 119
  rows go to the model; spec 003 targets 0.90, 0.80). Before rule 9b
  corrected v3, it called the two warehouse clubs `groceries` and the two
  card payments `debt_payment` (0.9906, 0.9664). On October 29 `categorize/v2`
  scored 0.9670 and 0.9474 in every run: it listed memberships under
  subscriptions, so Sonnet called `kqed membership`'s 5 gift rows
  subscriptions (issue #146). `SuiteUnavailable` without `ANTHROPIC_API_KEY`; scoring is
  unit-tested with a labeler that answers from the labels.
- `fixtures/pay_stubs/`: 30 synthetic pay stubs (text PDFs, clean and noisy
  PNG/JPEG scans, scanned PDFs; three layouts, `ledger`, `summary` and
  `advice`, each in all five outputs) with `<id>.json` labels beside each.
  Stubs 11-30 were appended in M10, so stubs 01-10 and their labels are
  unchanged; regenerating rewrites every file, so keep an old document whose
  bytes changed only through PDF metadata (`git checkout` it). Generated by
  `gen/make_pay_stubs.py` from a fixed seed with WeasyPrint and pypdfium2 (`DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib uv run python -m
  evals.gen.make_pay_stubs` on macOS). A test regenerates the labels and
  compares them with the committed JSON; the rendered bytes depend on installed
  fonts, so they are committed and not compared. SSNs are in the never-issued
  900-999 area.
- `suites/extraction.py` (`extraction`, LLM): the real pipeline and Sonnet over
  the stubs; `field_accuracy`, `document_accuracy`. Redaction runs before the
  model, so `extraction-smoke` scores it, at zero tolerance. Raises
  `SuiteUnavailable` (exit 2) without `ANTHROPIC_API_KEY`. Its baseline is
  measured: 1.0 on both in every live run on October 29, about 55 cents a run
  (spec 005 targets 0.95, 0.70).
- `suites/extraction_smoke.py` (`extraction-smoke`, free): the same pipeline
  with `FakeGateway`; checks every stub yields a proposal, SSNs are redacted,
  and neither the SSN nor an unmasked account number reaches the model input
  (image pages are OCR'd again to check). Needs the tesseract binary.
- `fixtures/calc/k401.json`: every spec 006 example (ids are the spec's test
  names, `spec-006-<name>`) plus the no-match edge case. A test fails if a row
  of the spec's example table has no case.
- `fixtures/calc/emergency_fund.json` and `health_plans.json`: every spec 011
  and 012 example (`spec-011-<name>`, `spec-012-<name>`), posted to `POST
  /calc/emergency-fund` and `POST /calc/health-plans`; the same coverage test
  runs over `NEW_CALCULATOR_SPECS`. `expected` holds only the fields an example
  states; a list in it (the plan costs, the break-even pairs) is compared item
  by item, each item by its stated fields.
- `fixtures/calc/w4.json`: every spec 014 example (`spec-014-<name>`, rows 1,
  2a, 2b and 3 to 10, and rule 10a's 11 to 15, the refund or balance due at
  the stub's withholding) posted to `POST /calc/w4`; `test_every_spec_014_example_is_a_case`
  fails on a table row with no case.
- `fixtures/benefits/`: 5 synthetic benefits summaries (`summary-0N.pdf`, text
  PDFs written by hand in Helvetica with no embedded font) and labels beside
  each, from `gen/make_benefits.py` with a fixed seed (`uv run python -m
  evals.gen.make_benefits`). They vary the layout (plan table or prose), 1 to
  3 plans, the match wording (tiered, single, dollar for dollar, none) and the
  vesting wording; one prints a 900-area SSN and an HSA account number. The
  bytes depend only on the seed, so a test compares both the PDFs and the
  labels with a fresh generation. Tier labels are cumulative, the way the
  proposal computes them from the printed bands.
- `suites/benefits_extraction.py` (`benefits-extraction`, LLM): the real
  pipeline, `extract_benefits/v2` and `benefits_proposal` over those
  summaries; `plan_field_accuracy`, `retirement_accuracy`,
  `document_accuracy`. `SuiteUnavailable` without `ANTHROPIC_API_KEY`; its
  baseline is measured: 1.0 on all three in every live run on October 29,
  about 6 cents a run (spec 013 targets 0.90, 0.80, 0.60). Scoring is unit-tested with a reader that answers from the labels.
- `fixtures/explain/decisions.json`: 29 synthetic `k401_match` inputs (with
  optional benefits passages) covering under-match, capped, catch-up,
  compensation-capped, already-full and no-match cases, each with the rate its
  pay stub shows (`pay_stub_contribution_pct`, null for no stub; spec 008 rule
  7a): 11 at the chosen rate, 14 at another (issue 132's stub-01 case among
  them: 3% on the stub, 5% chosen), 4 with no stub. Results are computed by the
  suite, never stored.
- `suites/explain.py` (`explain`, LLM): the real draft-verify-retry-fallback
  flow (`verify.flow.run_explain`) with `LLMGateway` over those decisions, the
  seed citations read from `api/db/seed/irs_citations/`, no database.
  `first_try_verified`, `no_fallback`, `cited`. Its baseline is measured:
  1.0 on all five metrics in three live runs on October 30, about 47 cents a
  run (spec 008 targets 0.8, 0.95, 1.0). `rate_framing` (issue
  132): over the 18 decisions whose stub shows another rate or none, the share
  whose final row does not claim the chosen rate is already in effect, as an
  LLM judge reads it (`Gateway.judge_rate_claim`, `judge_rate_claim/v1`, spec
  008 rule 24a): it is sent the chosen rate, the stub's rate (null for no
  stub), the full-match rate and the final row's words, and works out which
  rate each present-tense sentence describes, so "If you stay at the 4% on
  your pay stub, you already get the full match" is no claim while "You
  already earn the full match" is one when the stub shows less. A failure
  line quotes the judge's sentence; a judge error counts as a miss and the run
  goes on. It measures drafts and never gates one. `judge_accuracy` checks the
  judge: the share of the hand-labeled items in
  `fixtures/explain/rate_claims.json` (37: 18 claims, 19 not, 7 of them live
  sentences of a named fixture decision whose rates they carry; spec 008 rule
  24b) it reads as labeled. When a run's `rate_framing` drops, read its
  `judge ...` failure lines first. The judge's prompt never quotes an item (a
  test checks). `SuiteUnavailable` without `ANTHROPIC_API_KEY`; scoring is
  unit-tested with scripted judges.
- `fixtures/explain/w4_decisions.json`: 12 synthetic `w4` inputs (spec 014
  examples), each with what its pay stub withholds a paycheck
  (`pay_stub_withholding_cents`, null for none; spec 008 rule 7b): 6 another
  amount than the entries (issue 181's decision, example 11 at stub-01's
  $272.44, among them; one more, one nothing, one within a dollar), 3 the
  entries' own amount, 3 no stub. The first one, example 9 with no stub, is the
  smoke suite's W-4 decision.
- `suites/explain_w4.py` (`explain-w4`, LLM): the explain flow and model over
  those decisions; `first_try_verified`, `no_fallback`, `cited` as in
  `explain`, and `withholding_framing` (issue 181): over the 9 decisions whose
  stub withholds another amount or none, the share whose final row does not
  call the entries' withholding or their projection what happens now, as the
  `judge_withholding_claim/v1` judge reads it (`Gateway.judge_withholding_claim`,
  spec 008 rule 24d; it is sent both withholdings, both outcomes in words and
  the row's words). `judge_accuracy` is the share of the 24 hand-labeled items in
  `fixtures/explain/withholding_claims.json` (10 claims, 14 not; rule 24e) it
  reads as labeled. A suite of its own so the 401(k) suite's metrics and
  baseline keep their meaning. Its baseline is measured: 1.0 on all five metrics in three live runs on October 30, 21 to 23 cents a run. `SuiteUnavailable` without
  `ANTHROPIC_API_KEY`; scoring is unit-tested with scripted judges.
- `suites/explain_smoke.py` (`explain-smoke`, free): the same flow with
  `ScriptedGateway` over eight scripted runs (pass, fail-then-pass,
  fail-twice on a 401(k) decision; pass and fail-twice on the first W-4
  decision in `fixtures/explain/w4_decisions.json`, spec 014 example 9; a pass
  on issue 132's decision that states the stub's rate, spec 008 rule 7a; a
  pass and a fail-twice on issue 181's W-4 decision whose draft and fallback
  state the stub's withholding, rule 7b);
  `flow_correct`
  checks rows, the retry's feedback and that the fallback verifies and is
  cited. Fixture entries name their `calculator` (default `k401_match`) and
  `load_decisions` computes results through `calc/registry.py`.
- `suites/recurring.py` (`recurring`, free): spec 009's `sync.recurring.detect`
  over two labeled histories, no database. `recorded-sandbox` is the recorded
  Plaid `/transactions/sync` page in `api/tests/fixtures/plaid/recorded/`,
  parsed by the production `PlaidProvider`, with hand labels in
  `fixtures/recurring/recorded_sandbox_labels.json`. `custom-user` is a Plaid
  custom sandbox user (`fixtures/recurring/custom_user.json`, pasteable into
  the dashboard as a `user_custom` password) with labels in
  `custom_user_labels.json`, both written by `gen/recurring_user.py` from a
  fixed seed (`uv run python -m evals.gen.recurring_user`; a test fails on
  drift). Labels come from how each series was built, never from the detector.
  `precision`, `recall` (matched by `merchant_norm` and cadence) and
  `fields_exact` (typical amount and overdue flag of the matches). The baseline
  records one known miss: a utility bill swinging about 22% around its median
  falls partly outside the 15% series (spec 009, edge cases).
- `suites/checkin.py` (`checkin`, free): spec 015's finders
  (`checkin.findings.all_findings`) over `fixtures/checkin/scenarios.json`,
  one case per row of the spec's finder table (`spec-015-<test name>`; a test
  fails when a row has no case). Each case holds the facts with fixed ids and
  the expected findings typed in from the spec's arithmetic, only the payload
  fields the spec states. No database. `precision`, `recall` (matched by
  kind and key) and `fields_exact` (severity and the labeled payload fields).
- `baseline.json`: the committed metrics every run is compared with.
- `nightly.py` and `.github/workflows/nightly.yml`: every day at 09:17 UTC
  (and on `workflow_dispatch`) the workflow runs `--suite all` when the
  `ANTHROPIC_API_KEY` secret is set, else `--suite free` with a notice, capped
  at `EVAL_MAX_COST_CENTS` (300). On a non-zero exit it renders the report
  with `python -m evals.nightly` and opens the `nightly-evals` issue ("Nightly
  evals regressed"), or edits the open one and comments the run link, then
  fails. Close the issue once fixed; the next regression opens a new one.

## Rules

- Metrics are scores in [0, 1], higher is better.
- Deterministic suites (`llm=False`) tolerate no drop (`run.DETERMINISTIC_TOLERANCE`).
  An LLM metric may drop below its baseline by 2 points (`run.LLM_TOLERANCE`) or by
  one case's worth, whichever is larger (`run.tolerances`). A case is one thing the
  model gets right or wrong on its own: a field, a document, a decision, a
  merchant's label. Its worth is the largest share of the metric one case
  decides; the suite reports it per metric in `SuiteResult.case_worth`, and a
  metric it leaves out is a share of the suite's `cases`, worth `1 / cases`. So
  one answer the model gets wrong on one run and right on the next never fails
  the nightly by itself, while a second miss on a small metric, or a slide of
  more than 2 points on a large one, does. Today: benefits `document_accuracy`
  and `retirement_accuracy` (5 summaries) 20 points, extraction
  `document_accuracy` (30 stubs) 3.3, extraction `field_accuracy` (390 fields) and benefits
  `plan_field_accuracy` (72) 2, categorization `llm_accuracy` 11.8 and
  `accuracy` 2.6 (one label covers all 14 `sunrise bakery` rows, of the 119 the
  model labels and the 534 in all), explain 3.4 (29 decisions), its
  `rate_framing` 5.6 (a share of only the 18 it scores) and its
  `judge_accuracy` 2.7 (37 calibration items); explain-w4 8.3 (12 decisions), its `withholding_framing` 11.1 (a share of the 9 it scores) and its `judge_accuracy` 4.2 (24 items). A metric above its baseline passes. The
  report gives each metric's tolerance under `tolerances`. `test_run.py` checks
  the rule through the CLI; each LLM suite's tests check its `case_worth`.
  A metric that does not depend on the model belongs in a free suite, which
  tolerates nothing, never in an LLM suite (why `extraction` leaves
  `redaction_recall` to `extraction-smoke`).
- A new suite needs a registry entry and a baseline entry (a test checks both).
- Update the baseline only with `--update-baseline`, in a commit of its own, with
  the reason in the message.
- An LLM suite's baseline is what it measures live, not its spec's target: run
  it at least twice, check the runs agree within the tolerance, record one with
  `--update-baseline` and give every run's numbers and cost in the message. The
  target is what the measurement has to clear before it is recorded.
- Calc cases go through the HTTP route as a fixed eval user, never by calling
  `calc/` directly, so routing and serialization are covered too.
- LLM suites charge `Budget` before reading each result and use only synthetic
  fixtures; never real pay stubs or real bank data.
