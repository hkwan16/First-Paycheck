# 005: Pay stub and benefits extraction, review and confirm

Status: Implemented, M2. The `extraction` eval suite first ran live on October 29 (issue #123): on `claude-sonnet-5-5` every run scored `field_accuracy` and `document_accuracy` 1.0 over the 30 stubs for 55 to 56 cents, and the baseline holds those measurements. Rule 24a (`annual_salary_cents` on the stub output) added in M10. Rules 9, 10 and 23 name replaced documents since spec 004 rules 24-31. Rule 24b (`retirement_contribution_pct`, the 401(k) rate the stub shows) added for issue 132. Rules 22a-22e (one current stub per paycheck; a newer confirm supersedes) added for issue 190. Rule 1a (a dash or a zero printed on a line is 0, not null), prompt `extract_pay_stub/v2`, rule 22f (`DocumentOut.superseded`) and stubs 31-34 added for issues 195 and 199. Measured on November 1 over the 34 stubs: v1 scored `document_accuracy` 0.9118 and `field_accuracy` 0.9932 (stubs 31, 33 and 34 read a dash as null) for 63 cents; v2 scored 1.0 on both in two runs, for 64 and 63 cents, so the baseline's 1.0 holds. Rule 25a (one pay schedule, the newest stub's before the profile's) added for issue 198. Rule 24c (the salary check: a newer stub whose yearly pay differs from the saved salary asks which to use) and the profile's `salary_pay_stub_id` added for issue 221.

## Goal

Turn the redacted pages of spec 004 into a proposal the user reviews field by field, then store exactly what the user confirmed. The extraction runs as the `ingest.extract` job in the worker (spec amendment 1): Claude Sonnet 5.5 reads redacted text and redacted page images and returns typed JSON; plain code turns it into reviewable fields with roles, links each field to the redacted line it came from, and enforces gross minus deductions equals net on confirm (spec amendment 17). Code: `api/llm/schemas.py`, `api/llm/prompts/extract_pay_stub/v2.md`, `api/llm/prompts/extract_benefits/v1.md`, `api/llm/gateway.py` (`extract_pay_stub`, `extract_benefits`), `api/jobs/handlers/ingest_extract.py`, `api/ingest/proposal.py`, `api/calc/pay_stub.py`, routes in `api/app/routers/docs.py`, `api/app/routers/pay_stubs.py`, `api/app/routers/profile.py`, eval suites `evals/suites/extraction.py` and `evals/suites/extraction_smoke.py`.

## Inputs

| Input | Type | Valid range |
|---|---|---|
| `POST /docs/{id}/extract` | path id | A document of the user's with a blob, status not `confirmed`, type `pay_stub` or `benefits` |
| Model pages | `TextPage(number, text)` or `ImagePage(number, png)` | Redacted per spec 004; at least one |
| `POST /docs/{id}/confirm` | `{"pay_stub": PayStubValues}` or `{"benefits": {"plans": [PlanValues]}}` | Rules 16-21 |
| `PUT /profile` | `ProfileIn` | Rule 25 |

## Outputs

- `PayStubExtraction` and `BenefitsExtraction` (model output, never stored as confirmed data).
- `documents.proposal` (jsonb): `{fields, line_items, plans, source_lines, withheld_pages, notes}`, returned by `GET /docs/{id}` when the status is `proposed` or `manual_entry_required` (the redacted lines to type from), and null otherwise.
- `jobs.result` for `ingest.extract`: `{document_id, status, page_count, redaction_count, withheld_pages}`. Ids and counts only, never extracted text (spec 001 rule 28).
- On confirm (200): one `pay_stubs` row, which supersedes the current stub of the same paycheck and the stub of a document it replaced (rules 22a-22e), or `benefits_plans` rows plus `benefits_chunks`; the blob deleted; `documents.status = confirmed`, `confirmed_at` and `deleted_at` set. The response is `{document, pay_stub, plans}`: the document as `GET /docs` lists it and what was stored.
- `GET /pay-stubs`: current confirmed stubs (rule 22c), newest pay date first, each with `annual_salary_cents` (integer cents or null, rule 24a) and `retirement_contribution_pct` (a two-place percentage string or null, rule 24b). `GET /profile`, `PUT /profile`: the profile.

## Rules

### Schema (`llm/schemas.py`)

1. `ExtractedField[T]` is `{value: T | null, confidence: 0..1, source_text: string | null}`. `value` is null when the document does not show it; `source_text` is the printed line the value was read from, copied as it appears, `[REDACTED]` included.
1a. **A dash or a zero is an amount** (issue 195). A line the stub prints for an amount field with a dash (`-`, `--`), `0.00` or `$0` where the amount goes shows that nothing was taken: its value is `0` and its `source_text` is that line, so the proposal links the field to it (rule 18) and the person confirms $0.00 like any other value. The value is null only when the stub prints no line for the field at all (or the amount cell is unreadable). The line is also a line item with `amount_cents` 0 and its `field`. `extract_pay_stub/v1` said "a dash or a blank where an amount would be is null", so on November 1, 2026 the Acme stub's `401(k) -` came back null at 90% and the person could not confirm it without typing a zero.
2. `PayStubExtraction` has one `ExtractedField` per `pay_stubs` column the stub prints: `employer_name` (text), `pay_date`, `period_start`, `period_end` (ISO dates), `pay_frequency` (`weekly`, `biweekly`, `semimonthly`, `monthly`), and the this-period amounts in integer cents `gross_cents`, `federal_withholding_cents`, `social_security_cents`, `medicare_cents`, `state_tax_cents`, `retirement_contribution_cents`, `medical_premium_cents`, `net_cents`. It also has `line_items` and `notes`.
3. `other_deductions_cents` is not a model output: it is a sum, and the model never does money math. Each `LineItem` is `{label, amount_cents, kind, field}` with `kind` one of `earning`, `tax`, `pre_tax_deduction`, `post_tax_deduction`, `net`, `info` and `field` naming the column above that the line is already counted in, or null. Code computes `other_deductions_cents` as the sum of `amount_cents` over line items whose kind is `tax`, `pre_tax_deduction` or `post_tax_deduction` and whose `field` is null.
4. `BenefitsExtraction` is `{plans: [PlanExtraction], notes}`; `PlanExtraction` has `ExtractedField`s `name`, `kind` (`hdhp`, `ppo`, `hmo`), `premium_per_period_cents`, `deductible_cents`, `oop_max_cents`, `coinsurance_pct` (the member's share, 0 to 100), `employer_hsa_cents`, `enrollment_deadline`.
5. Prompts `extract_pay_stub/v2` (rule 1a; `v1` before issue 195) and `extract_benefits/v1` use purpose `extract` (model `LLM_MODEL_EXTRACT`, Sonnet 5.5), effort `low`, and their schema.

### Gateway (`llm/gateway.py`)

6. `extract_pay_stub(user_id, pages, job_id=)` and `extract_benefits(...)` send one user message whose content is every image page as a base64 PNG `image` block, in page order, followed by one `text` block that lists which page numbers the images are and then each text page as `Page N (text layer):` and its redacted text. Everything else (budget first, cached system prompt, `output_config` with effort and the JSON schema, no temperature, no prefill, refusal checked before the output is read, schema validation, the `llm_calls` row) is spec 003 rules 21-27.
7. A call with no pages raises `ValueError` before anything is sent or recorded.
8. `FakeGateway` answers extraction from `api/tests/fixtures/llm/extract_pay_stub.json` and `extract_benefits.json`, through the same budget, validation and ledger code.

### The `ingest.extract` job

9. `POST /docs/{id}/extract` locks the document row, and returns the current job's id when the document is `extracting` and that job is still `queued` or `running` (idempotent while running). Otherwise it queues a new `ingest.extract` job with payload `{document_id}`, sets `status = extracting`, `extract_job_id` and clears `status_reason`, and returns `{job_id}` (202). A replaced document is 409 `document_replaced` (spec 004 rule 28), a confirmed or deleted one 409 `document_confirmed` or `document_deleted`; an `offer_letter` is 422 `extraction_unsupported`. From `manual_entry_required` it queues only when the reading was unavailable (`no_model`, `budget`, `extraction_failed`), which `can_read_again` says; after `refused` or `no_readable_page` it is 409 `document_already_read` (spec 004 rules 32-35).
10. The job reads the blob in one short user session, then runs `prepare_document` (spec 004) and the gateway call with no transaction open, then writes the outcome in one user session, only while the document is still `extracting` under this job and has not been replaced (spec 004 rule 28).
11. **Proposed.** With at least one usable page and a valid model answer, the document becomes `proposed` with `proposal`, `redaction_count` and `page_count`.
12. **Manual entry.** No usable page (`no_readable_page`), a refusal (`refused`), a spent daily budget (`budget`), or no model (`no_model`: the worker has no gateway, which only happens outside production (spec 003 rule 12a), or the call raised `LLMMisconfigured` because the API rejected the key or the model id, spec 003 rule 24) makes the document `manual_entry_required` without retrying, keeping `redaction_count` and `page_count` and a proposal with the redacted source lines and no fields filled.
13. A schema error or any other API error (rate limit, 5xx, timeout, connection failure, other 4xx) raises so the queue retries (spec 002 rule 34); on the fifth and last attempt the job instead marks the document `manual_entry_required` (`extraction_failed`) and succeeds.
14. An unreadable file (spec 004 rule 9) marks the document `failed` (`unreadable_file`) without retrying. A document with no blob (deleted meanwhile) ends the job with `{"status": "skipped"}`.
15. The gateway never receives page text or images that were not redacted: text pages carry `redact_text` output and image pages the `redact_image` output; withheld pages are not sent.

### The proposal (`ingest/proposal.py`)

16. Pay stub fields, in this order, with `kind` and `role`: `employer_name` (text, info), `pay_date`, `period_start`, `period_end` (date, info), `pay_frequency` (text, info), `gross_cents` (money, gross), `federal_withholding_cents`, `social_security_cents`, `medicare_cents`, `state_tax_cents`, `retirement_contribution_cents`, `medical_premium_cents`, `other_deductions_cents` (money, deduction), `net_cents` (money, net). Each carries `key, label, value, confidence, note, kind, role`. Money values are integer cents, dates ISO strings.
17. `other_deductions_cents` comes from rule 3 with `confidence` null and the note `From <labels>`, the labels joined with commas and a last "and" (`From CA SDI and Dental/Vision`), or `No other deductions listed`. Any other field whose value is null gets the note `Type it if the document shows it.` (before issue 209 these were `Sum of: <labels>` and `Not found on the document`; a stored proposal keeps the note it was written with). The model's self-reported confidence is shown as is; the UI marks below 0.9 for review (spec amendment 12).
18. `source_lines` are the redacted lines of every page that was read, in order, each `{page, text, field_key, redacted}`. `redacted` is true when the line contains `[REDACTED]`. A field's `source_text` links to the first unclaimed line that contains it after both are lowercased and whitespace-collapsed; failing that, for money fields, the first unclaimed line containing the value printed as dollars (`1,996.04`). A line links to at most one field.
19. Benefits proposals have one `plans` entry per extracted plan, each with its fields (all role `info`), and the same `source_lines`.

### Confirm

20. The body is validated by `PayStubValues` (or `PlanValues`), the value-typed twin of the extraction schema: dates are dates, money is strict integer cents (`gross_cents > 0`, the rest `>= 0`), `period_start <= period_end`, `pay_frequency` an enum or null, `employer_name` at most 200 characters. A unit test keeps its keys equal to the extraction's keys plus `other_deductions_cents`.
21. **Arithmetic gate.** `calc/pay_stub.py:balance` computes `deductions = federal + social security + medicare + state + retirement + medical premium + other deductions` and `difference = gross - deductions - net`. A non-zero difference is 422 `pay_stub_unbalanced` with `details = {gross_cents, deductions_cents, net_cents, expected_net_cents, difference_cents}`. The `pay_stubs` check constraint is the database backstop.
22. Confirm is allowed from `proposed` and `manual_entry_required` (manual entry is a confirm with every field typed). The values stored are the ones in the body, never the proposal's. In one transaction: insert `pay_stubs` (or `benefits_plans`, plus `benefits_chunks` from `chunk_words` over the proposal's redacted source lines joined by newlines), delete the blob, set `status = confirmed`, `confirmed_at = deleted_at = now()`, clear `status_reason`.
### One stub per paycheck (issue 190)

Before issue 190, uploading and confirming the same stub again stored a second `pay_stubs` row, and every reader counted both: on November 1, 2026 two copies of the Acme stub made October read "2 pay stubs" and "Gross pay, 2 stubs" at $5,416.66.

22a. **The same paycheck.** Two of a user's confirmed stubs are the same paycheck when they have the same employer, `pay_date`, `period_start` and `period_end`. The employer compares as `employer_key`, a column the database generates from `employer_name`: runs of whitespace become one space, the ends are trimmed, letters are lowercased, and a missing name is `''`. So "Acme Corp" and " ACME  corp" are one employer; "Acme Corp." is another, because nothing says two names that differ by more than spacing and case are one employer. All four must match: two employers paying the same period are two paychecks, and so is a check the same employer pays for the same period on another date (an off-cycle bonus).
22b. **A newer confirm supersedes.** Confirming a pay stub supersedes, in the confirm's transaction, (1) the current stub of the same paycheck (rule 22a), and (2) the current stub confirmed from any document the confirmed one replaced, directly or through a chain of replacements (spec 004 rules 24-26): Replace says the new upload takes that one's place, also when the person corrected its dates. Superseding sets the old row's `superseded_by_id` to the new stub's id. Nothing is deleted, so every stub confirmed and when stays on record, and the newer confirm leads, as a newer decision version does (spec 007). Superseding is final: a superseded row never becomes current again, never changes, and is never superseded a second time (a trigger refuses any other update; `authenticated` may update only `superseded_by_id`). The confirm response and the screens are unchanged: the copy simply counts once.
22c. **Current stubs.** A stub is current when its `superseded_by_id` is null. A partial unique index on `(user_id, employer_key, pay_date, period_start, period_end) WHERE superseded_by_id IS NULL` makes two current stubs of one paycheck impossible on any connection. One user's confirms run one at a time (a transaction-scoped advisory lock on the user, taken before the supersede), so two copies confirmed at once both succeed and the later one leads. `(superseded_by_id, user_id)` references `pay_stubs (id, user_id)`, so a stub is only superseded by one of the same user's; under row-level security a confirm never sees, let alone supersedes, another user's stub.
22d. **Every reader reads current stubs only**, through `db/pay_stubs.py:current_pay_stubs()`: `GET /pay-stubs` (rule 24, which the 401(k), W-4, health plan and emergency fund cards, Why and Confirm read), `routers/pay_stubs.py:newest_pay_stub` (`POST /explain` and whether a stored explanation is stale, spec 008 rules 7a, 7b and 19a), `GET /cashflow` and the check-in's cash flow (spec 010 rule 1), `paycheck_count` (spec 007 rule 26), the next expected pay date's anchor (spec 007 rule 16), `GET /plan` and its PDF (spec 016), and the check-in's two newest stubs (spec 015). `tests/unit/test_boundaries.py` fails on a query of `PayStub` anywhere else, so a new reader cannot count a superseded copy.
22e. **Stubs stored before the fix.** Migration `0020_pay_stub_superseded_by` applies rule 22b to the stubs already stored, in the order they were confirmed (`created_at`, then `id`), before it creates the unique index. A user who confirmed copies keeps the newest one current.
22f. **What Link shows for a superseded copy** (issue 199). `DocumentOut.superseded` (`GET /docs`, `GET /docs/{id}`, the confirm response) is true when the document's confirmed stub was superseded (rule 22b) and false otherwise, also for a document with no stub (not confirmed yet, or a benefits summary). It is read through `db/pay_stubs.py:superseded_documents`, one query for the whole list. The web then badges only the copy that counts "Confirmed" and says of the others that a newer copy replaced them.
23. Confirming a replaced document is 409 (`document_replaced`, spec 004 rule 28); confirming twice is 409 (`document_confirmed`); a document whose file was deleted is 409 (`document_deleted`); one not yet read (`uploaded`, `extracting`, `failed`) is 409 (`document_not_ready`). A body for the wrong type (`benefits` for a pay stub) is 422 (`wrong_document_type`), and a body with neither or both keys is 422.

### Reads and profile

24. `GET /pay-stubs` returns the user's current stubs (rule 22c) ordered by `pay_date DESC, created_at DESC`, every column including the generated `tax_year`. A superseded stub is not listed.
24a. **Yearly salary the stub implies.** Every stub output (`PayStubOut`: `GET /pay-stubs` and the confirm response's `pay_stub`) carries `annual_salary_cents`: `gross_cents` times the pay periods a year for its `pay_frequency` (weekly 52, biweekly 26, semimonthly 24, monthly 12), from `calc/pay_stub.py:annual_salary_cents`. It is an integer product of integer cents, so no rounding is applied and it need not be a round figure. A stub with no `pay_frequency` gives null. It is computed on read, never stored, and it is not written to the profile: the client offers it as the starting salary in the plan details form, which the user saves with `PUT /profile` (the profile's own `salary_cents` wins when set, and a newer stub that disagrees with it asks which to use, rule 24c). Gross on one stub can include overtime or a bonus, which is why it is a starting value the user can change, not a confirmed salary.
24b. **401(k) rate the stub shows.** Every stub output also carries `retirement_contribution_pct`: `retirement_contribution_cents` as a percentage of this paycheck's `gross_cents`, `retirement_contribution_cents * 100 / gross_cents` computed exactly and rounded half up once to two places, from `calc/pay_stub.py:retirement_contribution_pct`. It is a `Decimal` with exactly two places, sent as a JSON string (`"3.00"`), like every percentage the API returns (`calc/types.py:ResultPercent`). It is the same arithmetic as spec 015's `actual_pct`. A stub with no retirement line (stored as 0) shows nothing going to the 401(k), so its rate is `"0.00"`, not null. It is null only when it cannot be computed: a gross of zero or less, which confirm refuses (rule 20), so a stored stub has one in practice. It is computed on read, never stored, and never written to a decision: it is what the person contributes now, which the 401(k) card starts from (spec 006 rule 14) and the explanation states beside the rate the person chose (spec 008 rule 7a). Payroll can round a per-paycheck deferral to the cent, and a flat-dollar election is no whole percentage at all, so the rate need not be a round figure.
24c. **The salary check** (issue 221). The profile's `salary_cents` is a figure the person saved once; the pay schedule is the newest stub's (rule 25a). After a newer stub on another schedule or at other pay, the two come from different paychecks, and every step that reads both works from a year nobody confirmed: issue 221's account saved $95,000.10 from stub-01 ($3,653.85 x 26), then confirmed the Acme stub ($2,708.33 x 24 = $64,999.92), and the 401(k) and W-4 steps worked from $95,000.10 over 24 paychecks, $3,958.34 a paycheck, more than the new stub's whole gross pay, with nothing on screen saying so. The API never changes the salary itself (the person confirms everything); it asks.
    1. **What was compared.** `profiles.salary_pay_stub_id` (nullable; a composite same-user foreign key to `pay_stubs (id, user_id)`, `ON DELETE SET NULL (salary_pay_stub_id)`; migration `0022_salary_pay_stub`) names the stub the person last compared their salary with. `PUT /profile` takes it like every other field (null when left out, rule 25); an id that is not one of the user's stubs is 404 `not_found`. The client sends the newest stub's id when the person answers the question below, and when they save plan details with a salary other than the saved one (typed, or taken from the stub, with that stub on hand: `plan-details.ts:salaryStubId`); every other save passes the stored value through, so saving another field never answers the question for them.
    2. **When to ask.** `ProfileOut.salary_review` (`GET /profile` and `PUT /profile`, computed on read in `app/salary_review.py`, never stored) is set exactly when all of these hold: `salary_cents` is set; the newest current stub (rule 22d) has an `annual_salary_cents` (rule 24a; null without a pay frequency); it differs from `salary_cents`; and it differs from the `annual_salary_cents` of the stub `salary_pay_stub_id` names, current or superseded. Otherwise it is null. The comparison is exact, in cents, like the figures themselves.
    3. **What it says.** `{pay_stub_id, pay_stub_date, frequency, periods_per_year, gross_cents, annual_salary_cents, salary_cents}`: the newest stub, the yearly pay it comes to, and the saved salary, so a screen can say both in words without working anything out.
    4. **The answer.** While it is set, the 401(k), health plan and W-4 steps ask in place of their calculator (spec 018 rule 5d), with one action to take the stub's figure and one to keep the saved one: "Use $64,999.92" saves `salary_cents = annual_salary_cents` with `salary_pay_stub_id = pay_stub_id`; "Keep $95,000.10" saves `salary_pay_stub_id = pay_stub_id` alone. Either clears it. Until then no step works out a number from that salary, and every saved decision that reads the salary needs review (spec 007 rule 19c).
    - **Why ask instead of following the stub.** Gross on one stub can include overtime or a bonus (rule 24a), and a stub can be read or typed wrong; only the person knows whether it is their new pay. Following it silently would write a document's figure into a confirmed field, which nothing else in the product does.
    - **Why compare yearly pay, not stub ids.** A stub the person already answered for stays answered through the next paycheck at the same pay, which is a new stub with the same `annual_salary_cents`, and through a second copy of the same paycheck (rule 22b), so a person is asked again only when a stub says something new. A profile saved before this rule names no stub, so it is asked once if the newest stub disagrees.
25. `GET /profile` returns the saved profile, or the defaults (nulls, empty lists, `dependents = 0`) when none is saved. `PUT /profile` replaces it: `salary_cents` strict int > 0 or null; `salary_pay_stub_id` one of the user's pay stubs or null (rule 24c); `pay_frequency`, `filing_status`, `expected_healthcare_usage` enums or null; `other_jobs` a list of up to 5 `{annual_wages_cents > 0}`; `dependents` 0-20; `start_date` a date or null; `match_tiers` up to 5 tiers `{employee_pct_upto, employer_pct}` with both in (0, 100] and `employee_pct_upto` strictly ascending (spec 006); `vesting_years` 0-10 or null. Percentages are decimals with at most 2 places, sent and returned as JSON strings.
25a. **One pay schedule** (issue 198). Both `GET /profile` and `PUT /profile` return `pay_schedule`, the pay schedule every calculator card and every decision side effect uses (spec 007 rule 16, spec 014 rule 10a), or null. It is `{frequency, periods_per_year, source, pay_stub_date}`, resolved in one place, `app/pay_schedule.py:pay_schedule`, computed on read and never stored:
    1. The newest current stub (rule 22d, in `GET /pay-stubs` order) when its `pay_frequency` is set: `source = pay_stub`, `pay_stub_date` that stub's `pay_date`.
    2. Else the profile's `pay_frequency` when set: `source = profile`, `pay_stub_date` null.
    3. Else null. `periods_per_year` is the frequency's count from `calc.pay_dates.PERIODS` (52, 26, 24, 12). Only the newest stub is read: an older stub's schedule never fills in for a newer stub that prints none.
    - **Why the stub wins.** A confirmed stub is a document fact: the schedule payroll paid on, from a paycheck the person checked field by field. The profile's `pay_frequency` is an entry the person typed once, and nothing updates it. Issue 198's account saved "every two weeks" in its plan details while an older stub said so, then confirmed a stub paid twice a month, and every card kept using 26 paychecks: the emergency fund's per-paycheck amount, the W-4's withholding, and the health plan's yearly premiums were figured on the wrong paycheck, and the W-4 dropped its comparison with the stub (spec 014 rule 10a). With the newest stub first, a new stub takes effect on every card the moment it is confirmed, and the W-4 always compares against a stub on its own schedule. The profile's entry still serves a person with no stub yet, or whose newest stub prints no schedule.
    - **Seeing and changing it.** The plan details form always shows the schedule. From a stub it is read-only text naming the stub's pay date, with the way to change it: add a newer pay stub (or replace a misread one, spec 004 rules 24-31). From the profile, or with none, it is a choice saved with the form. The emergency fund card, the one card that needs only a schedule, asks for it when there is none. The client never copies a stub's schedule into the profile: that copy is what went stale. A profile entry under a newest stub that states a schedule is kept as typed and not used.

### Evals

26. `extraction` (LLM): for each of the 34 labeled synthetic stubs in `evals/fixtures/pay_stubs/` (10 since M2, 20 more in M10: three layouts, every layout in all five outputs, 15 of them noisy PNG or JPEG scans or scanned PDFs; 4 more for issue 195, stubs 31-34, each printing one deduction line as a dash or `0.00`, labeled 0 by rule 1a), run `prepare_document`, the real gateway with an in-memory ledger that charges the run's budget, and the proposal builder. `field_accuracy` is the share of labeled fields (13 per stub: `pay_frequency`, the three dates and the nine money fields including the computed `other_deductions_cents`; a column the stub does not print is labeled null) whose proposed value equals the label exactly; `document_accuracy` the share of stubs with every one of them right. Redaction runs before the model and does not depend on it, so this suite does not score it: rule 27's `extraction-smoke` gates it at zero tolerance, where an LLM suite would tolerate one case's worth. Targets, which a measurement has to clear before the baseline records it: field accuracy at least 0.95 on the 34-stub set (0.90 on the M2 set of 10), document accuracy 0.70. A run costs about 63 cents (Sonnet, one call per stub); the nightly workflow caps the whole run with `--max-cost-cents`. Without `ANTHROPIC_API_KEY` the suite is unavailable and the runner exits 2.
27. `extraction-smoke` (free): the same pipeline with `FakeGateway`; `pipeline_ok` is the share of stubs that produce a proposal, `redaction_recall` the share of stubs labeled with an SSN whose `redaction_count` is non-zero (target 1.0), and `ssn_free` the share of stubs whose model input contains no labeled SSN or unmasked account number, checked on text pages directly and on image pages by OCR'ing the redacted PNG again.

## Edge cases

- A deduction cell left blank on a line that prints its label: null (nothing shows the amount), unlike a dash or `0.00` (rule 1a). In practice payroll prints one or the other, and the person types the amount either way.
- A stub the model reads with gross missing: the proposal shows the field null with its note; the user must type it before confirm passes rule 20.
- Benefits text over 400 words becomes several chunks; under it, one; a benefits document with no readable text writes no chunks.
- `POST /docs/{id}/extract` on a `failed` (unreadable) document queues another attempt while the blob exists; after retention deletes the blob it is 409.
- A refused document is confirmed by hand: the model read it and declined, so reading again is 409 `document_already_read` (spec 004 rule 35). Before issue #163 it could be read again, though nothing on screen offered it.
- A key the API rejects (an unfunded account answers 401) sends the document to manual entry (`no_model`) on the job's first attempt, with one `api_error` row; once the key works, the user can read it again ("Read again", spec 004 rules 32-34).

## Out of scope

- Offer letter extraction (the type is accepted on upload; extraction and confirm return 422 until a later milestone defines its schema).
- Inferring pay frequency from the period dates, and updating the profile from a confirmed stub. The client prefills the salary in `PUT /profile` (rule 24a) and saves a newer stub's only when the person chooses it (rule 24c); the schedule needs no copy (rule 25a).
- `GET /benefits-plans` and using benefits chunks in explanations (M6).
- The Batches API for extraction.
